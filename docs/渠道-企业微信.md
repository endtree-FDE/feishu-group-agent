# 企业微信适配器设计

这是设计，不是已经能上线的渠道。代码里的 `channels/wecom.py` 只把回调收成核心认识的事件，并且声明自己缺哪些能力。默认不加载，加载了也不连接。

结论先说：**第一版应该接「智能机器人」的 WebSocket 长连接，不接群机器人 webhook，也不把自建应用当成收消息的主通道。** 家用电脑没有公网地址，这和飞书用 lark-cli 长连接是同一类原因。

下面的限制和字段以企业微信开发者中心在 2026-10 仍公开的文档为准。官方页面以后会改，落地前要再对一次链接。

## 三种官方入口

| | 消息推送（原群机器人） | 智能机器人 | 自建应用 |
|---|---|---|---|
| 官方文档 | [消息推送配置说明](https://developer.work.weixin.qq.com/document/path/99110)（页面写明最后更新 2025/08/07） | [接收消息](https://developer.work.weixin.qq.com/document/path/100719)、[长连接](https://developer.work.weixin.qq.com/document/path/101463)、[回调加解密](https://developer.work.weixin.qq.com/document/path/101033) | [接收消息概述](https://developer.work.weixin.qq.com/document/path/90238)、[消息接口概述](https://developer.work.weixin.qq.com/document/path/90235)、[回调配置](https://developer.work.weixin.qq.com/document/path/90930) |
| 能收群里 @ 吗 | 不能。只有一个 webhook，用来**往群里发** | 能。群聊里 @ 机器人，或单聊，才会推 `aibot_msg_callback` | 官方写明发送到群是应用自己建的群，并且「暂不支持接收群聊消息」 |
| 没有公网时能收吗 | 不能收 | 能。长连接由本机主动连出去 | 不能。必须有公网可访问的 URL |
| 和本框架的关系 | 对不上。本框架不主动发消息，而它几乎只能主动发 | 对得上收和回 | 只能当补充：把加密 userid 换成明文、或者走会话存档。不适合当第一版的耳朵 |

## 为什么不是群机器人

[消息推送配置说明](https://developer.work.weixin.qq.com/document/path/99110) 的用法是向 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=KEY` 发 HTTP POST。它能发文本、markdown、图片、文件和模板卡片，文本最长 2048 字节。每个机器人 20 条/分钟。

文档特别要求保护 webhook 地址：泄漏之后，别人就能用它往群里发消息。本框架的配置会留在运行的电脑上，不能再加一把「谁拿到地址谁就能发言」的钥匙。

这条通道没有「用户在群里 @ 了机器人」的回调，所以做不了现在这种问答。骨架会拒绝配置里的 webhook，避免有人把它当成收消息的地址。

## 为什么不把自建应用当第一版

[接收消息概述](https://developer.work.weixin.qq.com/document/path/90238) 要求在管理后台填写 URL、Token、EncodingAESKey。企业微信用 GET 校验 URL，服务器要在 1 秒内把解密后的明文原样返回。之后的消息是 XML POST。服务器 5 秒内不回答会断线并重试，最多三次。

[加解密方案](https://developer.work.weixin.qq.com/document/path/90968) 是 AES-256-CBC。签名是 `sha1(sort(token、timestamp、nonce、msg_encrypt))`。EncodingAESKey 是 43 位，解码后 32 字节，IV 取密钥前 16 字节。自建应用的 receiveid 是企业 CorpID。

[消息接口概述](https://developer.work.weixin.qq.com/document/path/90235) 写的是：应用可以主动给成员发单聊，也可以收成员在应用里发的消息；发到群聊会话只针对应用创建的群，并且当时写明暂不支持接收群聊消息。这和「任意一个已有工作群里 @ 一下」不是同一件事。

[获取群聊会话](https://developer.work.weixin.qq.com/document/path/98914) 还要求调用方是自建应用、可见范围是根部门，而且群必须是这个应用创建的。不能拿它来给「机器人所在的普通群」做成员名单。

会话内容可以走另一套专区接口 [获取会话记录](https://developer.work.weixin.qq.com/document/path/100023)，但那是会话存档：要配公钥，应用要有「数据与智能专区」权限，只能拉 5 天，消息体还要再用私钥解开。它不是智能机器人回调的一部分，第一版不要接。权限太大，也不符合「只回答 @ 我的那一句」。

家用电脑没有固定公网 IP。要做 URL 回调就得再加内网穿透，多一个公网入口，Token 和 EncodingAESKey 也多一份要保管的密钥。飞书这边已经用长连接避开了这件事，企业微信不该退回去。

## 推荐：智能机器人长连接

[长连接文档](https://developer.work.weixin.qq.com/document/path/101463) 把两种 API 模式放在一起比较：

| | Webhook（设置接收消息 URL） | WebSocket 长连接 |
|---|---|---|
| 谁连谁 | 企业微信来连你的 URL | 你连 `wss://openws.work.weixin.qq.com` |
| 公网 | 要 | 不要 |
| 业务层加解密 | 要 | 不要。文档写底层已有加密 |
| 心跳 | 无状态 | 建议每 30 秒发 `ping` |
| 流式回复 | 企业微信反复回调你的 URL 来要下一段 | 你用同一个 `stream.id` 主动推，直到 `finish=true` |

适用场景里写了「无公网 IP」和「内网部署」。这就是本框架跑在自己电脑上的情况。

管理后台把智能机器人的 API 模式选成「长连接」，拿到 BotID 和一份长连接专用 Secret。这个 Secret 和 URL 回调用的 Token、EncodingAESKey 不是同一把。两种模式只能开一种，切换后另一种失效。

连接建立后发送：

```json
{"cmd": "aibot_subscribe", "headers": {"req_id": "..."}, "body": {"bot_id": "BOTID", "secret": "SECRET"}}
```

同一个机器人同时只能有一条有效长连接。新的订阅成功会把旧连接踢掉。这和本框架「一个应用只有一个接收进程」是同一条约束，骨架不能为了热备去开第二条。

官方有 Python SDK（文档里的 aibot-python-sdk）和 [Node SDK](https://github.com/WecomTeam/aibot-node-sdk)。落地时优先用官方 SDK 做心跳、重连和文件解密，不要自己拼 WebSocket 帧。骨架现在不导入这些包，避免飞书部署多一个依赖。

### 收消息

用户在群里 @ 机器人，或在单聊里发消息，服务器推 `aibot_msg_callback`。字段和 [接收消息](https://developer.work.weixin.qq.com/document/path/100719) 的明文一致，长连接不再包一层 encrypt。

| 官方字段 | 核心字段 |
|---|---|
| `msgid` | `message_id`。用来去重。文档写明可能重复推 |
| `chatid` | 群的 `chat_id`。单聊可能没有，适配器要用 `p2p:` 加 userid 补一个稳定编号 |
| `chattype` `group` / `single` | `group` / `p2p` |
| `from.userid` | `sender_id` |
| `text.content` | `content` |
| 群消息 | 适配器补一条提到自己的 `mentions`，核心的「是不是 @ 我」才过得去 |

`from.userid` 在创建者是超级管理员时是明文，否则是企业内的加密 userid。明文转换要另接自建应用，文档写在接收消息的字段说明里。第一版应把加密 userid 当成不透明编号：白名单里填什么，回调里就得是什么。不要把飞书的 `ou_` 和这里的 userid 放进同一个字段还假装是同一个人。

长连接支持的消息类型：文本、图文混排；图片、语音、文件、视频只在单聊。群里没有这些附件回调。能力表里因此不要在群聊路径上假装有 `attachments`。骨架现在连单聊附件也不下载。

`enter_chat`（用户当天第一次进入单聊）是事件，不是提问。[接收事件](https://developer.work.weixin.qq.com/document/path/101027) 允许回复欢迎语。本框架不主动发消息，适配器必须丢掉这个事件，不能回欢迎语。

### 回消息

收到回调之后用 `aibot_respond_msg` 回复，并且带上回调里的 `req_id`。流式更新用同一个 `stream.id`，10 分钟内要 `finish=true`，否则服务器自动结束。模板卡片用 `aibot_respond_update_msg` 更新。

频率（长连接文档「回复消息」一节）：收到回调后 24 小时内可以往该会话回。回复和主动推送加在一起，每个会话 30 条/分钟、1000 条/小时。进度如果做成流式刷新，一次回答会吃掉多条额度，核心要有自己的更新间隔，不能每来一个字就推一次。

官方还有 `aibot_send_msg`，可以在没有这条用户消息时往会话里推。文档写：需要用户先在会话里给机器人发过消息，之后才能推。本框架的红线是不主动发消息。适配器不要实现这个命令，看门狗、进群、欢迎语都不走它。

### 和飞书进度卡片的差别

飞书能发一张卡片再原地改。企业微信长连接的对应物是流式消息和模板卡片，不是飞书的 card JSON。骨架因此**不声明** `cards`、`card_update`、`reactions`、`recall`、`edit_text`。核心看到没有这些能力，就退回「一条文字回复」，不调用还不存在的更新接口。

等真的接上流式回复，再把 `card_update` 加进能力表，并且把 10 分钟和每分钟条数写进进度层。在那之前不要让模型以为企业微信有飞书卡片。

### 历史、成员、文档、日历、表格

智能机器人的回调里没有「拉取本群最近几天消息」或「列出群成员」的接口。

- 群历史：没有。`history` 不声明。停机补答依赖历史，这个渠道上会跳过，只靠本机已经见过的消息去重。
- 群成员：没有。`p2p.allow_group_members` 打开时，核心查不到名单就拒绝，不会放行。私聊仍可以靠显式名单和写入白名单。
- 云文档、日历、多维表格：不是这个机器人的接口。2026-03 的 [智能机器人更新日志](https://work.weixin.qq.com/nl/index/openclaw) 提到长连接可以通过文档 MCP 建文档和智能表格，那是另一套可选能力，第一版不接。没接之前 `docs`、`calendar`、`bitable` 都不声明，模型输出这些工具会被核心拒绝，确认码也不会发出。

自建应用的日程和文档接口以后可以做成同一个适配器上的可选能力，但要单独的企业凭证，不能和 Bot Secret 混用，也不能默认打开。

## 若以后不得不用 URL 回调

只在长连接不可用时才考虑。约束如下，都来自 [回调和回复的加解密方案](https://developer.work.weixin.qq.com/document/path/101033) 和 [接收消息](https://developer.work.weixin.qq.com/document/path/100719)：

- 智能机器人的 receiveid 传空字符串，不是 CorpID。
- GET 校验要在 1 秒内返回解密明文，不能加引号、不能带 BOM、不能带换行。
- POST 体是 `{"encrypt": "..."}`。先验 `msg_signature`，再解密。验签失败直接拒绝，不要把密文交给模型。
- 被动回复也要加密。5 秒内来不及答完时，先回空包，再在允许的窗口里主动回复。本框架的模型经常超过 5 秒，所以 URL 模式不能在同一次 HTTP 里等模型。
- `msgid` 去重。企业微信会重试。
- URL、Token、EncodingAESKey 只放环境变量或本机受权限保护的文件，不进 git，不进日志。
- 用户跟同一个机器人最多三条消息同时进行。核心已有的并发上限要小于或等于这个数。

这些都不在当前骨架里实现。

## 安全

- Bot Secret 只从环境变量读。配置里写 `wecom.secret_env` 的名字。出现 `secret`、`token`、`encoding_aes_key` 或 webhook 时，骨架拒绝加载，报错不包含那段值。
- 不保存、不记录 subscribe 帧。日志里不能出现 Secret。
- 不实现 `aibot_send_msg`，也不回复 `enter_chat`。
- 加密 userid 只当编号。不拿它去拼公网 URL，避免把身份带到外站。
- 确认码、白名单、脱敏、限流、SSRF 仍在核心。适配器只搬运已经脱敏的正文。
- 一个 BotID 一条连接，和本机单实例锁一起用。被踢掉时重连，不要同时起两个进程。
- 官方 SDK 的依赖以后单独加。飞书的默认安装路径不能因为企业微信而多装包。

## 骨架现在做什么

`channel` 写成 `wecom` 且 `channels.experimental` 为 true（或本机设置 `AGENTBOT_EXPERIMENTAL_CHANNELS=1`）时，才会构造 `WeComChannel`。

它会：

- 声明 `receive`、`send_text`、`identity`。
- 把一条 `aibot_msg_callback` 收成核心的事件。群消息补上对机器人的 mention。`enter_chat` 丢掉。
- `ready()` 返回假。正式启动因此在连接之前退出。

它不会：

- 打开 WebSocket，不会发 HTTP，不会读环境变量里的 Secret。
- 出现在没写 `channel` 的飞书配置的启动路径上。

## English

Use the WeCom intelligent bot’s WebSocket long connection (`wss://openws.work.weixin.qq.com`, [doc 101463](https://developer.work.weixin.qq.com/document/path/101463)). It needs no public callback URL. The group webhook ([doc 99110](https://developer.work.weixin.qq.com/document/path/99110)) can only push into a group. A self-built app ([doc 90235](https://developer.work.weixin.qq.com/document/path/90235)) needs a public URL and, as documented, does not receive ordinary group chat. The skeleton is experimental, off unless `channels.experimental` is true, and it never connects. It must not send proactive messages, must not store the bot secret in config, and must leave confirmation codes, redaction, and SSRF checks in the core.
