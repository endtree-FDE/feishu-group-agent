# 断线提醒与早晨摘要

这两项都默认关着。旧的 `agents/*.json` 不写 `alerts` 和 `digest` 时，行为和以前一样：不发私聊，也不往群里发定时消息。

密钥不要写进配置。主人的 open_id 和群编号会写在你自己的 json 里，那个文件不要提交。

## 为什么需要断线提醒

看门狗每 5 分钟看两件事：进程还在不在，以及 `state/heartbeat` 是不是超过 3 分钟没更新。心跳线程大约每 60 秒写一次这个文件，**长连接断了它仍会写**。所以会出现这种情况：进程还活着，心跳也是新的，群里的 @ 已经没人接，看门狗却不重启，也不出声。

断线提醒补的是这一段。进程自己每大约 15 秒看一次长连接。日志里出现 `feishu-websocket: connected` 或 `ready event_key=` 算连上；写明断开、关闭、重置才算断开。群里长时间没有人说话不算断开。

通知不走事件长连接。核心把正文交给当前渠道的 `push_text`。飞书适配器再调用 `im +messages-send`，这是单独的发送接口，不会启动收消息的进程。长连接断了，只要这台电脑还能访问飞书、profile 还登录着，私聊就能发出去。企业微信还是实验骨架，这项会失败，不会去连接。

进程真的退出、或心跳超过阈值时，看门狗在重启**之前**再跑一次 `python agentbot.py <配置> --alert-check`。这条命令不拿单实例锁，不启动收消息的进程，也不改心跳文件。`alerts.enabled` 不是 `true` 时，看门狗不调用 Python。通知失败也不会挡住重启。

两边共用 `state/health_alert.json`。已经发过的中断不会因为重启再刷一条。

## 断线提醒怎么发

连续不健康达到 `unhealthy_after_sec`（不写是 180 秒）才发第一条。没到时间的闪断不发。之后每隔 `repeat_sec`（不写是 1800 秒）最多再提醒一次。恢复后发一条，只发一次。写成 `0`、负数或无法转成数字时，仍按 180 和 1800，不能靠改小到 0 把防抖关掉。

正文先按 `redact.txt` 脱敏，并去掉点名所有人的标记。日志只记动作和发出了几条，不写 open_id。本机记录在 `logs/alerts.log`。`local_log` 不写或为 `true` 时都会写；写成 `false` 才不写这份文件。

`owner_open_ids` 为空时不发飞书，只写上面的日志。`REPLACE_` 开头的占位符会被丢掉。

`windows_toast` 默认 `false`。只有写成 `true`、系统是 Windows、并且飞书没有发给每一位主人时，才尝试弹一次本地通知。

看门狗重启进程的条件仍是心跳超过 3 分钟，和 `unhealthy_after_sec` 无关。这项如果写成大于 180，进程已经死掉时，看门狗会先把进程拉起来，死亡告警可能来不及发。长连接断了但进程还在时，计时在进程内部，不受这 3 分钟限制。想两种情况都通知，就留着 180。

没有心跳文件（还没启动过）不告警，避免第一次安装就发一条。

## 早晨摘要怎么发

这是框架里唯一会主动发到群里的消息，而且只有 `digest.enabled` 为 `true` 才发。到了 `time`（默认 `08:30`，时区默认 `Asia/Shanghai`）之后的 `window_min` 分钟内（默认 30），给 `chat_ids` 里、并且已经在服务范围内的每个群发一条。服务范围是：`chat_ids`（配置顶层那个）非空时只用它；留空时用已经认下的群。

`window_min` 写成 `0` 表示只在那一分钟。写成负数时按 30。`time` 不是 `HH:MM` 时不发。时区认不出来时不发，不会猜一个。

一条里可以有两段：今天的团队日历，以及任务表里还没完成的行。日历编号用 `tools.calendar_read.calendar_id`，没有再用 `write.resources.calendar_id`。任务表用 `tools.base_read` 的 `base_token` 和 `table_id`。空的、或 `REPLACE_` 开头的，当成没配置，不会去读。两段都没配置就不发。`include_calendar` 或 `include_tasks` 写成 `false` 就关掉那一段。

完成与否看 `status_field`（默认「状态」）是否和 `done_values` 里的某一项完全相同。不写这个列表时，认「已完成 / 完成 / 已关闭 / 关闭 / 取消 / 已取消 / done / closed / cancelled / canceled」。「未完成」不会被当成「完成」。标题默认从「任务、标题、名称、事项」里找，也可以用 `title_field` 指定。负责人和截止日期只取文字，不把 open_id 或记录编号放进群里。

正文不调用模型。客户名、手机号和工具标记会先处理掉。`@所有人`、`@全员`、`@all` 和 `<at ...>` 会删掉，不会点名所有人。

每个群、每个本地日历日最多一条。重启也不会再发。程序先在 `state/digest_state.json` 占坑，再发送。发送明确失败会放掉名额，窗口里还可以再试。超时或看不懂结果时留着名额，避免同一天再发一条。日历和任务都没读到时不占坑，大约 5 分钟后再试，窗口过了就不再发。跨过午夜的窗口算开始那一天，23:50 和次日 00:10 不会各发一条。

打开摘要后，提示词稳定前缀里会多一句固定说明：这不是模型这一轮要写的，回答里也不要点名所有人。这句话不随问题和日期变化。关掉摘要时，这句不出现。

`/状态` 只在对应开关打开时多一行。两项都关着时，正文和以前一样。

演练（`--dry-run`）、`--check` 和 `--doctor` 不发这两类消息。

## 配置

```json
"alerts": {
  "enabled": false,
  "owner_open_ids": [],
  "unhealthy_after_sec": 180,
  "repeat_sec": 1800,
  "local_log": true,
  "windows_toast": false
},
"digest": {
  "enabled": false,
  "time": "08:30",
  "timezone": "Asia/Shanghai",
  "chat_ids": [],
  "window_min": 30,
  "include_calendar": true,
  "include_tasks": true,
  "status_field": "状态",
  "title_field": "",
  "done_values": ["已完成", "完成", "已关闭", "关闭", "取消", "已取消", "done", "closed", "cancelled", "canceled"]
}
```

`owner_open_ids` 填主人的 open_id，可以多位。`digest.chat_ids` 填要接收摘要的群。这些编号放在你自己的配置里，不要提交，也不要写进本文档。

## 飞书这边要准备什么

断线私聊用的是应用以机器人身份发消息，权限 `im:message:send_as_bot`。回复群消息本来就要这项，不用为了提醒再加一项。不需要打开 `features.p2p`，也不需要 `im:message.p2p_msg:readonly`（那是收私聊，不是发私聊）。

主人要在应用的可用范围里。如果发送失败、提示不在会话里，请主人先给机器人发一条私聊，建立会话后再等下一次提醒。提醒失败时，本机 `logs/alerts.log` 仍有记录。

早晨摘要的群里，机器人必须已经在里面。同一项 `im:message:send_as_bot`。

另外两项目标配置了真实编号才需要，占位符或空着不用加：

- 要读团队日历：`calendar:calendar.event:read`
- 要读任务表：`base:record:read`

改完权限后，到开放平台发布新版本，可用范围包含主人，以及摘要要发到的那些群的成员。`--doctor` 会按已经启用的摘要列出缺的权限。
